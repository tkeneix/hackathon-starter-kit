# AI 駆動開発チェックリスト

## 1. プロジェクト立ち上げ時（テンプレートで用意済みの項目は ✓ を確認するだけ）

- [ ] Git 管理・リモート・`.gitignore`・秘密情報の除外を設定した（テンプレート + `flow.sh init`）
- [ ] `CLAUDE.md` に技術スタック、構成、主要コマンド、ルールへの導線だけを書き、薄く保っている
- [ ] 1 ファイル 1 責務を基本に、ディレクトリ構成を決めた
- [ ] アーキテクチャ・テスト・レビュー・ログ・DB のルールが `.claude/rules/` にあり、`paths` が実際の構成と合っている
- [ ] 単体・結合・E2E、lint、typecheck、build を 1 コマンドずつ実行でき、`CLAUDE.md` に書いてある
- [ ] 秘密情報は自分で管理し、`.claude/settings.json` の deny で AI のファイル操作から `.env` 等を守っている
      （Bash 経由の間接的な読み取りは防げないため、必要ならサンドボックスや PreToolUse フックを検討する）
- [ ] main のブランチ保護と CI を設定した（`flow.sh protect --execute`）

## 2. タスクごと（8 ステップ）

- [ ] 実装前にプランを書き、AI の質問で要件の曖昧さを除いた（Step 1）
- [ ] 人間が P0 要件・受け入れ条件・スコープ外を承認した（Step 1）
- [ ] 設計・セキュリティ・運用・ビジネスの観点別にプランをレビューした（Step 2）
- [ ] テストケース一覧を、人間が業務・利用者の視点で確認した（Step 3）
- [ ] 承認済みプランだけを実装し、口頭で要件を追加しなかった（Step 4）
- [ ] Red を確認してから Green にした（Step 5）
- [ ] 必須のテストと品質コマンド・ゲートをすべて実行した（Step 5）
- [ ] 独立レビューを P0 が無くなるまで繰り返し、P1 は対応か受け入れを記録した（Step 6）
- [ ] 人間が差分・設計判断・残存リスク・影響範囲・ロールバックを確認した（Step 7）
- [ ] 承認・マージ・外部操作は、人間の指示で行った

## 3. 週次（ハッカソン中は日次）

- [ ] 「コードは通るが動かない」事象が起きていないか、起動設定とログを確認した
- [ ] 不要な skip、過剰な mock、脆いセレクタ、偶然成功するテストが無いか確認した
- [ ] 同じ指摘が繰り返されていないか確認し、恒常的なものはルールや Skill に昇格した
- [ ] 巨大ファイル、重複、責務の混在などの劣化の兆候を確認した
- [ ] 定期リファクタリングを実施し、テストが Green の状態を維持した（Step 8）
- [ ] 古い・矛盾する指示を削除し、deny パターンが実際のリポジトリと合っているか確認した

## 4. 品質が崩れたとき: X → Y → F

症状だけを直さず、この順で原因をさかのぼる。

- [ ] **X: コンテキスト** — プランやルールが必要十分で、最新で、一貫しているか。古い文書や矛盾するルールが混ざっていないか
- [ ] **Y: テスト** — 正しい理由で失敗するか。常時成功、skip、網羅の穴、実装への過結合が無いか
- [ ] **F: モデル／設定** — X と Y を確認した後で、モデル・推論の強さ・並列化・ツールを見直す

コンテキストとテストが壊れたままモデルだけ替えても、品質は安定しない。

## 5. チームで運用するとき

- [ ] 共通ルールは「書き込み禁止」「破壊的コマンド禁止」「認証情報の隔離」など少数の強い制約に絞った
- [ ] 設定は `.claude/settings.json`・git hooks・CI で機械的に強制し、個人の善意だけに依存していない
- [ ] 認証・権限・データ削除・LLM への個人データ送信など重要箇所は、必ず人間がレビューした
- [ ] うまくいったルール・Skill・プロンプトは、テンプレート（キット）側にも反映した
