# 8 ステップ開発プロセス

曖昧な要求を、根拠のある仕様 → 検証可能なテスト → レビュー可能な差分へ変える経路を固定するためのプロセス。
AI にコードを書かせること自体が目的ではない。

## 1. なぜ分けるのか

AI 開発の失敗は、コード生成能力よりも次の構造で起きやすい。

- 要件が曖昧なまま実装へ進む
- 実装者とレビュアーが同じ文脈・同じ思い込みを共有する
- テストが実装後の追認になり、誤った仕様まで固定する
- 「守ってください」という文章を安全制御だと誤認する
- AI が出した差分を、人間が理解しないまま承認する

そこで開発を、計画 → 観点別レビュー → 実装 → テスト → 再レビュー → 人間判断に分け、3 種類の品質保証を重ねる。

1. **入力品質**: 質問とプランで、実装前に曖昧さを減らす（Step 1〜3）
2. **工程品質**: Red-Green-Refactor と観点別レビューで、誤りを小さい単位で見つける（Step 4〜6）
3. **判断品質**: 最後に人間が、目的・リスク許容度・説明責任を引き受ける（Step 7）

## 2. 適用範囲

**すべての作業に 8 ステップをフル適用する**（2026-09-23 決定）。機能追加、挙動を変える修正、マイグレーション、
セキュリティに関わる作業、分析コード、ツール・設定の変更を含む。

例外: typo・書式だけの変更は、人間が明示的に認めた場合に限り、Step 1〜3・6 を省略してよい
（その場合も PR と人間レビューは経る）。

## 3. 全体像

| Step | 内容 | 担当 | 出口条件 | 使うもの |
|---|---|---|---|---|
| 1 | プランドキュメント作成 | 人 + Claude | 要件・設計・テスト計画を**人が承認** | `/plan-document`、[雛形](../templates/plan-document.md) |
| 2 | プランの観点別レビュー | 独立レビュアー | P0 解消、P1 の扱いを決定 | `design-reviewer`・`security-reviewer`・`operations-reviewer`・`business-reviewer` |
| 3 | テスト網羅性レビュー | 独立レビュアー | 要件とテストケースが対応。**人が業務上の期待を確認** | `test-coverage-reviewer` |
| 4 | 承認済みプランの実装 | Claude | プラン外の変更なし | `.claude/rules/` |
| 5 | テスト実装・全通過 | Claude | Red 確認後 Green、全品質コマンド成功 | `/tdd` |
| 6 | 実装の観点別レビュー | 独立レビュアー | P0 解消、P1 は解消か受け入れを記録 | `/eng-practices` の後に `design-reviewer`・`edge-case-reviewer`・`security-reviewer` |
| 7 | 人間レビュー | 人 | 意図・リスク・影響範囲を理解して**承認** | `/create-pr` で作った PR、`flow.sh approve` |
| 8 | テスト駆動リファクタリング | Claude + 人 | 振る舞いを変えず Green を維持 | [プロンプト集](prompts.md) §8 |

時間は上限ではない。小さな変更では短く、認証・権限・データ削除・LLM への個人データ送信などでは厚くする。

## 4. 二つのフィードバックループ

- **ループ A（Step 1〜3、実装前）**: レビューで不足があれば Step 1 へ戻る。コードが無いので直すのが安い。
- **ループ B（Step 4〜6、実装後）**: 実装・テスト・レビューを往復する。テストが通るだけでは終わらない。

終了条件は「AI が指摘しなくなった」ではなく、**P0 がゼロで、P1 の採否に理由があり、プラン・テスト・差分の
対応が説明できること**（[.claude/rules/review.md](../../.claude/rules/review.md)）。

## 5. 各ステップの手順

### Step 1: プランドキュメント

1. 人が目的・利用者・解きたい問題を示す。
2. Claude はすぐ書かず、技術・UX・データ・権限・運用・失敗時の挙動を一問ずつ確認する。
3. Claude が `docs/plans/<yyyymmdd>-<短い内容>.md` に要件・設計・テストケース・実装順・スコープ外を書く。
   推測した箇所は明示する。
4. **人が P0 要件と受け入れ条件を承認する**。AI に「何を作るべきか」の最終決定を委ねない。

### Step 2: プランの観点別レビュー

- 設計・セキュリティ・運用・ビジネス整合性を、**別々の**レビュアーに割り当てる（評価基準を混ぜない）。
- 指摘は P0/P1/P2 に分類し、根拠と失敗シナリオを付ける。プランの「レビュー記録」に残す。P0 は実装前に解消する。

### Step 3: テスト網羅性レビュー

- テストは要件から導く（実装の形から逆算しない）。正常系、境界値の両側、異常系、権限、外部障害、回帰を確認する。
- **人は、テスト一覧が本当に業務上の期待を表しているか確認する**。

### Step 4: 承認済みプランだけを実装する

- プランにない要件や追加機能は入れない。新しい要件や大きな設計変更が見つかったら、実装を止めて Step 1 へ戻る。

### Step 5: Red を確認し、全テストを通す

- 新規テストが修正前に失敗することを確認する。最初から通る場合は、実装済み・検証が弱い・対象の誤りのどれかを調べる。
- 対象テストだけでなく、結合・E2E・lint・typecheck・build とゲート（`tools/bin/flow.sh check`）まで通す。

### Step 6: 実装の観点別レビュー

- `/eng-practices` でセルフレビューした後、設計・境界と異常系・セキュリティのレビュアーを独立して実行する。
- レビュアーは読み取り専用（Read・Grep・Glob のみ。コマンドは実行しない）。呼び出す側が差分と検証結果を渡す:
  `mkdir -p .review && git diff origin/main...HEAD > .review/diff.patch`（`.review/` は gitignore 対象）。
  Red/Green の結果はプランか依頼文に書いて渡す。全観点に同じ入力を渡す。
- Step 4〜6 を、P0 がゼロになり、すべての P1 が解消または人間に受け入れられるまで繰り返す。

### Step 7: 人間レビュー

`/create-pr` で PR を作成し（PR 作成は自動。2026-09-23 決定）、GitHub 上の PR で人間がレビューする。
コードの量ではなく次を確認する。

- 変更が解決する問題と利用者価値
- データと権限の流れ
- 主要な設計判断と代替案
- プランと実装の差分
- 壊れた場合の影響範囲とロールバック
- AI が「不明」とした点

人間が「承認して」「マージして」と指示したら、`tools/bin/flow.sh approve` → `tools/bin/flow.sh merge` を実行する
（[git-workflow.md](../git-workflow.md) §3）。

### Step 8: テスト駆動リファクタリング

- 機能追加と混ぜない（別ブランチ・別 PR）。関連テストが Green の状態から始める。
- 一度に一つだけ変更し、毎回テストを再実行する。壊れたらその変更を戻す。
- 巨大ファイル、責務の混在、重複、古いルールなど、長期的な劣化を定期的に戻す。

## 6. 人間が必ず介在する場所

| ゲート | 人間が決めること | AI に任せてよいこと |
|---|---|---|
| Step 1 完了時 | 目的、P0 要件、受け入れ条件、スコープ外 | 質問、文書化、候補案の比較 |
| Step 2・3 の後 | P1 の採否、残存リスクの許容、テストが業務上の期待を表すか | 観点別の穴探し、テスト案の列挙 |
| Step 4 開始前 | 実装着手の承認（Step 1 の承認と、P0 解消の確認） | 承認済みプランの実装 |
| Step 7 | 承認・マージ可否、説明責任、リリース判断 | 差分要約、影響の候補、証拠の整理、PR 作成 |
| 外部操作の前 | デプロイ、DB 変更、通知送信、ブランチ保護の変更 | 下書き、事前検証 |

## 7. Git 運用との対応

| Step | ブランチ・PR 上の作業 |
|---|---|
| 1〜3 | `tools/bin/flow.sh start <短い内容>` で作業ブランチを作り、プランを `docs/plans/` にコミットする |
| 4〜6 | 同じブランチで実装・テスト。コミットごとに pre-commit でゲートが走る |
| 7 | `tools/bin/flow.sh pr`（CI が走る）→ 人間がレビュー → 指示で `approve` / `merge` |
| 8 | 別の作業ブランチ・別 PR |

## 8. どこに何を書くか

| 内容 | 置き場所 |
|---|---|
| 毎回必要なコマンド・構成・禁止事項・ルーティング | `CLAUDE.md`（薄く保つ） |
| 対象パス固有の制約 | `.claude/rules/*.md`（`paths` で対象を指定） |
| 複数手順の作業（プラン、TDD、PR 作成、障害調査） | `.claude/skills/<名前>/SKILL.md` |
| 観点別の独立レビュー | `.claude/agents/*.md` |
| 必ず拒否する操作・毎回走らせる検査 | `.claude/settings.json`、git hooks、CI（文章ではなく機械的に強制する） |
| タスクごとの承認済みプラン | `docs/plans/` |

同じ指摘が繰り返されたら、会話で直すのではなくルールや Skill を更新する。品質が崩れたときの点検は
[チェックリスト](../checklists/ai-driven-development.md)の「X → Y → F」。
