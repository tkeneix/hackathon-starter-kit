# TDD

## 0. 開始条件

- 承認済みプラン（`docs/plans/`）と `.claude/rules/testing.md`、変更対象パスに適用されるルールを読む。
- 要件・承認済みプランを期待動作の根拠にする。現在の実装を正解として扱わない。
- 期待結果が曖昧、または仕様と実装が矛盾する場合は、推測でテストを書かず確認を求める。

## 1. テストリストを作る

- 変更後に観測できる振る舞いを、正常系、境界値の両側、異常系、権限、既存動作の回帰に分けて列挙する
  （プランの「新規テストケース」が起点）。
- 全テストを先に実装しない。設計を前へ進める最小の 1 件だけを選ぶ。

## 2. Red: 失敗を確認する

- 選んだ 1 件のテストを書き、そのテストだけを実行する（例: `uv run pytest path/to/test_x.py::test_name`）。
- 未実装の振る舞いが理由で失敗することを確認する。構文エラーや無関係な環境エラーは Red として数えない。
- 最初から成功した場合は、既に実装済みか、検証が弱いか、対象を誤っているかを判定して報告する。

## 3. Green: 最小限で通す

- その 1 件を通すために必要な最小の実装だけを加える。
- テスト専用分岐、固定値だけの返却、安易な skip で成功させない。
- 同じ失敗を繰り返す場合は、仮説を更新してから次の変更を行う。

## 4. Refactor: Green を保って整える

- 関連テストがすべて Green の状態でのみリファクタリングする。振る舞いを変えず、各変更後にテストを再実行する。

## 5. リストが空になるまで繰り返す

- 作業中に見つけたシナリオはテストリストへ追加する。
- 完了時は必須の品質コマンド（`uv run pytest`、`uv run ruff check .`、`tools/bin/flow.sh check` 等）を実行し、
  テストリストの各項目・実装したテスト・Red/Green の結果を対応づけて報告する。
